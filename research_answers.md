# Research Answers

## 1. Preserving application state across HTTP requests (authentication and sessions)

HTTP is a stateless protocol: every request-response cycle is independent, and the server keeps no built-in memory of previous requests. Web applications therefore add state on top of HTTP, most commonly with cookies and sessions. When a user logs in, the server verifies their credentials, creates a session record holding data about that user, and sends back a random session ID in a Set-Cookie header. The browser automatically returns this cookie with every later request, which lets the server look up the stored session and recognise the user without asking them to log in again. Django follows this pattern. SessionMiddleware loads the session from the "sessionid" cookie, and AuthenticationMiddleware uses it to attach request.user to each request. By default, session data is stored in the django_session database table, although cache, file and signed-cookie backends are also available. Calling login() stores the user's ID in the session and rotates the session key to prevent session fixation, while logout() flushes the session. Passwords are stored only as salted hashes. Cookies should be marked HttpOnly, Secure and SameSite to reduce theft and cross-site attacks, and Django's CSRF tokens protect state-changing forms. An alternative is token-based authentication, such as JSON Web Tokens, where the client sends a signed token with each request and the server stores nothing. This scales well but makes revoking tokens harder.

## 2. Migrating a Django project to a server-based database (MariaDB)

Moving a Django project from SQLite to a server-based database such as MariaDB involves several steps. First, install and start the MariaDB server, then create a database with the utf8mb4 character set and a dedicated user who has privileges on only that database. Second, install a database driver in the virtual environment; Django's MySQL backend works with MariaDB and normally uses the mysqlclient package, which needs system libraries such as the MariaDB development headers and pkg-config. Third, edit the DATABASES setting in settings.py: set ENGINE to "django.db.backends.mysql", then supply NAME, USER, PASSWORD, HOST and PORT (3306 by default), and set the charset option to utf8mb4. Credentials should be read from environment variables rather than committed to version control. Fourth, run "python manage.py makemigrations" if the models have changed, then "python manage.py migrate", which creates all the tables, including those for Django's built-in apps. Running "python manage.py dbshell" or creating a superuser is a quick way to confirm the connection works. If existing SQLite data must be kept, export it with dumpdata (excluding contenttypes and auth.permission) before changing the settings, and import it with loaddata afterwards. Finally, check the Django documentation to confirm that your MariaDB version is supported, and always back up data before migrating.
